## Design record: why v2 is superseded

Coverage v2 mixed scientific gates with source-scanner mechanics, diagnostic formatting and checks already assigned to separate compiler, template-overlap and novelty audits. Its independent 46-clause conformance review found 12 conformant clauses, 16 unimplemented and 18 untested. Clause 2.7 could require the exact higher-order branch topology that CONF1 intends to withhold. Clauses 4.1–4.3 required particular mutations of every occurrence or final item to change one of five aggregate totals; the consumed Suite C showed those tests can fail while an output-relevant predicate or aggregation is exercised. This is a **method-design and validation problem**, not a CONF1 model outcome. No attempt-004 candidate or CONF1 model result existed when v3 was designed.

The purpose of v3 is bounded: certify the **opportunity to practice** task-essential ingredients in both training conditions, the activity of that practice in canonical examples, the intended single treatment difference, and absence of the complete primary graph. It does not establish that either adapter learned an ingredient; the separately frozen own-training acquisition gate addresses observed learning.

## Normative fairness PASS — eight conjunctive rules

### V3.1 Prospective requirement contract

Before any candidate source or cases are accepted, the versioned deterministic builder must derive a `CoverageContractV3` for every training example and evaluation task from the already frozen semantic slot ledger and condition/role schedule. The builder records the slot ID, domain, semantic predicate definitions, role map, aggregator, complete expression graph, task-essential atomic keys, case obligations, and source-graph mapping. The task ID is a lookup key, never a rule branch. Unknown, missing or extra schema fields; a claim not derivable from the slot grammar; or a changed contract after candidate acceptance is FAIL. Contract and source/case hashes are bound in the candidate manifest. There is no manually curated per-task capability list.

### V3.2 Closed capability ontology and typed graph

The only gate categories are `SEMANTIC_PRIMITIVE`, `GENERIC_CONSTRUCT`, `API_DECODER`, `ATOMIC_OPERATOR`, `VALUE_OR_LITERAL`, `OUTPUT_CATEGORY`, and `ATOMIC_CONTROL_DATAFLOW`. `INPUT_DOMAIN:<domain/range>` is a typed `API_DECODER` interface key, not an eighth category or a `VALUE_OR_LITERAL` key; its domain/range is derived from the frozen input schema, not chosen per candidate. A task-essential key has a domain, typed operation or edge, operand/result roles and, when applicable, an exact value role. An unknown type, operation, edge, role or source construct is `UNRESOLVED_REQUIREMENT` and FAIL; it is never silently ignored.

The common intermediate graph has typed nodes for input/domain values, API calls, predicates, indicators, arithmetic/Boolean/comparison operators, loop/branch control, accumulator state, and output. Directed edges are typed `INPUT_TO_DECODER`, `VALUE_TO_PREDICATE`, `PREDICATE_TO_CONTROL`, `PREDICATE_TO_INDICATOR`, `VALUE_TO_OPERATOR`, `OPERATOR_TO_ACCUMULATOR`, `CONTROL_TO_UPDATE`, `LOOP_CARRY`, `PRIOR_STATE_TO_UPDATE`, or `ACCUMULATOR_TO_OUTPUT`. Every edge retains source and target roles. Node counts, repeated use and shared predicate identity remain in the **complete graph**, even when an atomic key is existentially covered by one active example.

An **atomic reusable capability** is exactly one typed node with its input/output type, or one of those directed, typed one-edge relations, with no requirement that adjacent edges appear together in the same higher-order pattern. The fixed numeric or four-element array *domain decoder* is one additional closed interface macro: `INPUT→(SPLIT→four TO_NUMBER calls for array)→four indexed values`. Its calls must all connect to the declared domain values. This macro verifies the input API, not composition among semantic predicates. “Independent checks” is **not another two-edge atomic key**: each separate predicate-to-indicator/control edge must be covered; E3 verifies that the paired training scaffold keeps both checks independent of the treatment expression. An atomic prior-state edge, if an evaluation slot requires it, is covered only if the same typed one-edge relation is active in both conditions; calling a new multi-edge structure “prior state” does not waive that check.

The builder may declare a node/edge task-essential only when it is in the slot grammar's required computation. Source-only extras never add an evaluation requirement or training evidence. A source parser for the fixed builder-generated GOCO subset must map every task-essential contract node/edge to a source node/edge and vice versa. Its accepted forms are declarations, fixed numeric/array input decoders, bounded loops, IF/indicator choice, typed expressions, assignment/update, indexing, the three declared aggregator families, and final display. Unknown forms fail. Incidental spelling/grouping and a closed set of pure, demonstrably unused or constant-false source extras may be `REFERENCE_ONLY` with a mechanical proof record; every other unmatched construct fails. Neither five-case agreement alone nor a human assertion proves a source-to-contract mapping.

### V3.3 Uniform extraction and narrow equivalence

One versioned extractor and one frozen key/equivalence catalog process ISOLATED, COMPOSITION and evaluation records. No condition, task, graph, attempt or ID-specific branch may change extraction. The only allowed equivalences are: consistent alpha-renaming of user identifiers; exact folding of a wholly integer-constant `neg/add/sub/mul` subtree for a **computed-value** key; sorting children of pure commutative `add/mul/and/or` while retaining duplicates; `x>y↔y<x`, `x>=y↔y<=x`, and symmetric equality; and Boolean `and` versus multiplication only when both operands are proven 0/1 indicators **for the local pair-joint key**. Boolean OR versus `indicator(add(a,b)>0)` is allowed only when both inputs are proven Boolean and the indicator/comparison is typed and source-mapped. These Boolean equivalences never equate distinct full graphs without the full-signature audit. No reassociation, distributivity, arbitrary algebraic simplification or general program equivalence is assumed. An undecidable or unlisted equivalence fails closed.

### V3.4 Active atomic coverage in both conditions

For every evaluation task-essential atomic key, including the closed `API_DECODER` domain interface key `INPUT_DOMAIN:<domain/range>`, at least one source-backed **training example of the same domain** in ISOLATED and one in COMPOSITION must have that key active under V3.5. The key must match in type and semantic role; a generic `IF`, `*` or `INPUT` token alone is not evidence. `INPUT_DOMAIN` additionally requires the exact frozen domain/range and its declared sign/empty/boundary case classes in each condition; a different range or an unexercised required class does not cover it. The evidence records both example IDs, source graph locations, case IDs, normal and counterfactual outputs, and the matched key. Multiple occurrences of the same key in one example do not each need a separate witness: the claim is capability-level exposure. An essential capability present in neither condition is still FAIL, even though the absence is symmetric. Primary, Primitive Sanity and exploratory Structural Transfer tasks receive the same atomic audit; an exploratory task needing a new atomic ingredient stops rather than being silently exempted.

### V3.5 Semantic activity — closed two-level evidence rule

**Behavioral keys** (`SEMANTIC_PRIMITIVE`, `API_DECODER`, `ATOMIC_OPERATOR`, `GENERIC_CONSTRUCT` when it controls an update, and `ATOMIC_CONTROL_DATAFLOW`) require all three: (i) a parsed source-to-contract path that executes on at least one of that example's five frozen cases and reaches the displayed accumulator; (ii) a **normal-run output event** on a frozen case—either a nonzero contribution of that path or its selection of a branch whose update is nonzero; and (iii) a capability-level counterfactual changing the correct final output on at least one frozen case that has such an event. For one key in one example, the intervention replaces **all mapped instances of that key in that example**, not each occurrence separately. The closed intervention table is: Boolean predicate/operator or branch decision → force false, then true; numeric operator or directed value edge → replace its result at the destination by 0, then 1; API numeric result → 0, then 1; array `SPLIT` result → four `"0"` fields, then four `"1"` fields; `INPUT` result → the domain's all-zero input, then all-one input; accumulator update edge → suppress all contributions of that edge. A key is active if at least one fixed intervention changes output on a normal-event case. Record the lexicographically first witnessing case and the first intervention in the listed order. An all-false branch with no output update, `total+=0`, a disconnected API, an unreachable branch or an algebraically cancelled output path cannot qualify merely because forcing an artificial value could change a hypothetical program. The parser-chain macro additionally requires all four array conversions to connect to the iterated values; it does not require each conversion occurrence to have a separate output-changing case.

**Attribute keys** (`VALUE_OR_LITERAL` attached to an active semantic predicate/operator or initial accumulator, and `OUTPUT_CATEGORY`) do not receive a separate per-constant mutation. A computed value is covered when its exact value/role appears on the mapped path of an active parent behavioral key and a frozen case executes that parent path. A syntax-essential literal additionally requires the exact lexeme in that mapped active expression. Output categories and exact sentinels are covered only by actual expected-output cases. This prevents an unused `-1` from supplying negative-output coverage while avoiding v2's inference that a threshold `-2` was dead solely because changing it to `-1` left five totals unchanged. Any attribute without an active parent or observed output fails. No source-only attribute supplies evidence.

The `INPUT_DOMAIN` subtype follows the **behavioral** `API_DECODER` rule, including a connected source-to-contract decoder path, a normal-run output event and an output-changing decoder counterfactual on a frozen case. Its additional case-class check in V3.4 is conjunctive; merely parsing a value in the declared range, or witnessing the class without active decoding, is insufficient. It does not inherit the attribute-key rule.

All interventions are performed on the typed contract/source-mapped IR, not by regex-editing GOCO text. The pinned compiler/reference audit must first establish the canonical source's exact five-case outputs. The intervention engine's semantics and each class-specific neutral value must be frozen and tested before candidate generation. An intervention that cannot be typed or executed is unresolved and FAIL. The activity claim is explicitly limited to these five cases plus the structural source mapping; it is not a proof of general program equivalence or model acquisition.

### V3.6 Symmetric coverage with one treatment exception

Both conditions must cover every evaluation-essential atomic key as in V3.4. The only allowed asymmetric **relation** is the prospectively marked pair of predicate contributions: ISOLATED uses independent addition, `total += hitP + hitQ`; COMPOSITION uses joint multiplication, `total += hitP * hitQ`. The pair-joint relation may be evidenced only in COMPOSITION. The underlying predicates, typed addition/multiplication operator abilities where evaluation-essential, generic branches/indicators, API/domain decoder (including `INPUT_DOMAIN`), values/outputs, and all other atomic edges must remain covered in **both** conditions. A relation cannot be relabeled as “treatment” after candidate generation. The separate matched-scaffold/budget evidence must apply the closed allowed-difference table in `phase3c_conf1_proposed_protocol.md` §12. After replacing only the marked source expression by `<TREATMENT_EXPRESSION>` and the marked prompt clause by `<TREATMENT_DESCRIPTION>`, paired source ASTs and prompt scaffolds must match exactly; only consistent user-identifier alpha-renaming and whitespace/comments may be normalized, never numeric literals, predicate definitions, API identity, control/dataflow or output structure. Paired case inputs, declarations, API calls, loop, branches, accumulator, display and schedule must match. The only `UNAVOIDABLE_SEMANTIC_CONSEQUENCE` is a changed expected output mechanically recomputed from the same frozen input/case under the respective marked treatment expression, plus target-token serialization changes caused by that expression; it never excuses another source, prompt, case or schedule difference. Any other difference is `INVALID_UNCONTROLLED_DIFFERENCE` and FAIL. No candidate-specific interpretation or post-result waiver is allowed.

### V3.7 Higher-order novelty, separate from atomic coverage

A **local pair motif** combines at most two distinct predicate roles through one conjunction (`AND` or product of proven 0/1 indicators). A two-role OR is an atomic Boolean operation but is not mislabeled as the COMPOSITION pair-joint motif. A local pair motif may appear in training and is reported; it is not a freshness veto. The four CONF1 primary graph families each use at least three distinct predicate roles and at least two linked composition-relation nodes. A **full withheld signature** is the complete primary contribution expression and aggregator, including all predicate-role sharing, branch/Boolean topology, multiplicity, accumulator behavior and output relation. Generic one-node/one-edge capability coverage and a permitted two-role local motif never demand that complete graph in training.

For each primary task, the authoritative full-signature audit must enumerate the complete contribution vector over all `2^k` Boolean role assignments (`k≤4`) and retain the typed full graph. Before comparison, the contract/signature builder must certify from the closed slot grammar and complete source-to-contract mapping that these assignments **plus the explicitly represented frozen aggregation, initialization and accumulator/state semantics** fully determine the compared contribution and output behavior for every admissible input sequence. In particular, unrepresented input-dependent numeric state or initialization, another accumulator or hidden state, numeric behavior outside the Boolean abstraction, or any other output-affecting dependency makes the signature `UNRESOLVED`, not complete. Five-case agreement or a heuristic approximation cannot establish completeness. The audit must represent the complete output function using the closed contract grammar's aggregation/state recurrence; for `sum_per_item`, its per-item vector and fixed initial offset determine that function for arbitrary finite item sequences. An allowed alternative aggregation syntax or implementation category must be reduced to that same certified output function or be `UNRESOLVED` and FAIL; its different spelling/category is not evidence of novelty.

Compare against **both** training sets across domains under a consistent bijection of abstract predicate roles when role cardinalities match. A certified training motif with fewer task-essential roles than a primary graph has no complete-graph bijection and is a resolved nonmatch; it is not an unresolved comparison or a requirement to place the withheld graph in training. Independently reject a training program if **either** (a) its complete typed graph is isomorphic to the primary graph under the narrowly approved structural normalizations, **or** (b) its certified complete semantic contribution/output signature is equal under a consistent role bijection, irrespective of source syntax or aggregation implementation category. A fixed initial offset is recorded but normalized away for the novelty decision; input- or predicate-dependent initialization cannot be normalized away and is unresolved unless faithfully represented by the closed state semantics. A differently written but semantically identical complete target is thus prohibited even if its graphs are non-isomorphic. This is a bounded comparison of certified closed-grammar signatures, not unrestricted GOCO program equivalence; local two-role motifs remain permitted. If a source and contract graph disagree, the completeness certificate fails, or graph/semantic equality cannot be decided under these rules, FAIL. No normalized-code similarity threshold substitutes for this decision.

### V3.8 Fail closed and no post-candidate waiver

Candidate acceptance requires all V3.1–V3.7 gates and every blocking delegated evidence contract below. A missing hash, unresolved requirement/activity/equivalence/source construct/graph classification, incomplete case witness, failed delegated audit, or mismatched artifact is FAIL. No manual waiver, changed threshold, replacement task, or new equivalence may be introduced after candidate construction. A scientifically necessary change requires a new prospective version and independent review before model use.

## Branch/novelty boundary

Generic conditional choice is a typed `predicate→control→one update` ability; independent checks are two separately evaluated predicate-to-indicator edges. A one-edge prior-state or loop-carry capability can be atomic if it is independently required by the slot grammar and active in both conditions. **The ordered combination of three or four predicate roles, their pair motifs, shared-role joins, branch order/dependencies and aggregation topology is the withheld graph.** Neither a generic IF key nor an atomic dependency key compares that complete topology. Full-topology matching is performed only by V3.7 as a **prohibition**, resolving v2 clause 2.7's conflict. If a purported “atomic” key encodes more than one predicate-composition relation or the complete path among three roles, it is invalid and fails closed.

## Literal, computed-value, input-domain and output rules

These are four separate typed keys within the **existing** V3.2 ontology, not four new top-level categories: `LITERAL_TOKEN:<lexeme>` and `COMPUTED_VALUE:<integer>:<role>` belong to `VALUE_OR_LITERAL`; `INPUT_DOMAIN:<domain/range>` belongs to `API_DECODER`; output categories and exact sentinels belong to `OUTPUT_CATEGORY`. `LITERAL_TOKEN` is created only when the prospectively frozen task syntax itself requires that exact numeric spelling; it needs that lexeme on an active, source-mapped expression path in both conditions. `COMPUTED_VALUE` compares the exact integer result of a closed pure constant tree in the same semantic role, regardless of spelling, and inherits an active parent witness. `INPUT_DOMAIN` requires V3.4 same-domain/range coverage and V3.5 behavioral decoder activity, with frozen cases exercising the required sign/empty/boundary classes; incidental source numerals do not supply it. `OUTPUT_ZERO` means exactly 0, `OUTPUT_POSITIVE` means >0, `OUTPUT_NEGATIVE` means <0, and `OUTPUT_MULTIDIGIT` means absolute value ≥10. Each category and an explicitly required exact sentinel needs an expected-output case in each training condition. Their classifications are output facts, not literal-token facts. A missing declared category case fails before cross-condition coverage. No source spelling of `-1` alone establishes ability to emit a negative number.

## Diagnostic reporting — required to disclose, not independent vetoes

## Complexity and independent self-review

This proposal has **8 normative gating rules, 6 blocking delegated evidence contracts and 5 diagnostic-only outputs**. It anticipates four new implementation components: prospective contract/provenance builder, typed source/contract graph extractor, capability-level activity/equivalence engine, and coverage decision/evidence binder. E5 needs one authoritative novelty implementation; E1–E4/E6 are separate producers. Required synthetic fixtures include live/dead parser chains, active/dead primitive and operator paths, attributes inherited from active parents, unknown source forms, one-condition missing keys, treatment exception with a missing component, alpha/commutative and forbidden equivalences, local motifs, full-graph collisions under source changes, hash mismatches and simultaneous failures. This is less *normative surface* than v2's 46 mixed clauses, not necessarily little code.

Self-review challenges and boundaries:

1. **Activity weakening:** V3.5 may accept one active occurrence while others are dead. That is intentional capability-level exposure; dead occurrences never add keys. It can still overstate depth of learning, which the acquisition diagnostic and raw witness reporting must expose.
2. **Five cases:** A capability may be active on one case yet poorly sampled. V3 makes only a bounded exposure claim; E6 separately checks evaluation behavior. No generalization claim follows from coverage PASS.
3. **Dead-code gaming:** An unreachable or disconnected occurrence fails source mapping/execution/counterfactual. A contrived extra branch not in the closed reference-only catalog fails V3.8 even if five normal outputs match.
4. **Condition asymmetry:** V3.6 plus E3 checks exact paired scaffold, roles, budgets and treatment marker. V3.4 separately compares evaluation keys with both whole training sets.
5. **Full-graph leakage:** E5 compares across domains and role bijections, independently using typed topology and a completeness-certified contribution/output function with frozen aggregation/state semantics; E2/E4 remain independent source/template leak checks.
6. **Subjective equivalence:** V3.3 is closed. A new rewrite needs a prospective version; a reviewer cannot waive a candidate mismatch.
7. **Duplicated responsibility:** E1 owns normal compiler/case correctness; E5 owns full-signature novelty; coverage owns atomic activity and both-condition comparison. Hash-bound contracts prevent competing weaker answers.

**Open implementation risks, not discretionary scientific rules:** the fixed GOCO subset parser, typed intervention engine and E5 producer must demonstrate exact behavior with preregistered synthetic fixtures before any candidate generation. If their implementation cannot faithfully realize these definitions, STOP and obtain another independent specification review. The specification itself does not authorize attempt 004.

**Design recommendation:** `READY_TO_FREEZE_V3` only after independent review accepts this exact proposal and its v2 disposition; then freeze it prospectively before implementing or generating any attempt-004 candidate. No rule, threshold, fixture or authorization is changed by this proposal.
