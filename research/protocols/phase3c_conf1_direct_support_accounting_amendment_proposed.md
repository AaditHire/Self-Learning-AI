## 1. Single gap, established findings, and effect

The accepted targeted requirement-bridge audit classified the blocker as
`FROZEN_ACCOUNTING_SPECIFICATION_GAP`. Selector satisfaction already exists in
the accepted generic binding machinery. That machinery distinguishes selected
contract/source occurrence pairs from dependency evidence; its accepted generic
readiness is not reopened or redesigned here. Audit/checkpoint/development
records describe behavior and are NOT scientific authorities.

The missing case is a fully represented raw semantic occurrence that does not
satisfy a prospective required selector, is not equivalence-internal or RO
eligible, but directly realizes a task-essential element of the unchanged
prospective contract's complete expression graph. Frozen amendment v2 has no
authorized direct-support entry for that case. This proposal supplies ONLY that
accounting meaning and representation; it does not pretend the existing schema
already allows it.

Exactly four final buckets remain:

1. `REQUIRED_DIRECT_MAPPING`;
2. `REQUIRED_VIA_AUTHORIZED_EQUIVALENCE`;
3. `AUTHORIZED_EQUIVALENCE_INTERNAL`;
4. `REFERENCE_ONLY`.

Inside `REQUIRED_DIRECT_MAPPING`, distinguish two proof bases, NOT two buckets:

| Direct-accounting role | Necessary proof basis | Ownership record |
| --- | --- | --- |
| Selector satisfier | The source occurrence actually satisfies one or more unchanged prospective selectors, with exact key/type/role/context/multiplicity and attachments | Existing `direct_required_mappings` entry; nonempty `required_occurrence_ids` |
| Direct required support | The non-selector source occurrence directly corresponds to an exact task-essential contract graph element and is necessary to a connected direct realization containing a selector satisfier | New `direct_required_support_accounting` entry; NO required-ID/key/attachment fields |

A supporting EDGE never inherits a head NODE's requirement identity. No new
requirement occurrence, ontology key, attachment, evidence kind, equivalence,
RO class, or independent V3.4/V3.5 exposure follows from the second role.

## 3. Contract graph identity and prospective task-essential classification

### 3.1 Distinct identity spaces

`requirement_occurrence_id` identifies a prospective selector obligation.
`contract_graph_element_id` identifies one NODE or EDGE in the complete
prospective graph. Source occurrence IDs identify original raw source elements.
These spaces MUST NOT be conflated, even when existing strings happen to match.

Use the existing addressable contract graph element ID wherever present. Do not
rename it, replace it with a parser ID from the candidate, or normalize it to a
capability key. References are qualified by owning contract and semantic kind;
zero/multiple matches or conflicting identities block acceptance.

ONLY when the bound graph has no stable addressable ID, define a lossless
deterministic address:

```text
RID("V32CONTRACTGRAPH", [program_id, contract_id, element_kind,
                       prospective_graph_ordinal])
```

Use D §3.3's exact RID framing. The ordinal is a minimal decimal string starting
at 1, over the complete graph's NODE list followed by EDGE list in its existing
prospective order. Preserve duplicates as distinct elements. Where lists are
derived from a prospective grammar, use its already defined deterministic order,
never candidate parse order, graph sorting by observed source, runtime iteration,
hash of a later report, or outcome-filtered order. If that order is not defined,
identity is UNRESOLVED; do not invent an ordering policy in an implementation.
The wrapper addresses the existing element without modifying its native record.
It is not a requirement ID, canonical key, scientific row or new artifact role.

The authoritative resolution root is the exact pre-bound contract's
`complete_expression_graph`, not a recursive search of arbitrary JSON. NODE and
EDGE partitions and any native selector path must be known from that contract's
closed schema. The wrapper ordinal selects precisely that partitioned element.
An unrecognized graph schema cannot be made usable by this proposal alone.

### 3.2 Mechanical element view

For each complete contract graph element, reconstruct a logical element view
from the unchanged contract, its original semantic graph/statement tree,
bindings, declared domain and required computation. The view supplies:

- owning `program_id` and `contract_id`, element ID, kind and prospective ordinal;
- operation/relation, datatype, operand/result types and roles;
- NODE binding/semantic role and ordered operands;
- EDGE source/target element IDs, direction and exact port;
- enclosing statement/region/control ancestry, loop identity and pass identity;
- applicable temporal state/read/write/decoder/output obligation;
- prospective task-essential classification and its frozen-contract derivation.

NODEs have no invented EDGE endpoints/port; EDGE descriptors retain their real
endpoints. All nullable/nonapplicable facts follow the bound contract's closed
schema, not a permissive extension dictionary. These facts are resolved rather
than redundantly copied into support entries. This view is not a new serialized
contract field, proof container, scientific population or replacement ontology.
Its information must already be present or uniquely reconstructible from the
prospective contract under V's frozen grammar. Missing necessary information is
UNRESOLVED, not permission to synthesize a fact from the source.

Task-essential classification is one of the logical findings `TASK_ESSENTIAL`,
`NON_TASK_ESSENTIAL`, `UNRESOLVED`. The first requires positive prospective
derivation as an element of the slot grammar's required computation under
V3.1/V3.2. Mere membership in a complete graph, a raw-key inventory, a producer
`essential` flag, or an implementation checkpoint is insufficient. Reconstruct
the classification from the bound graph's required-computation facts and frozen
semantic recipe; a flag unsupported by that derivation rejects.

Representational-only or non-task-essential elements remain in the COMPLETE
graph with their exact identities, but are mechanically excluded from the
task-essential obligation set and cannot use direct-support accounting. Unknown
classification is not presumed task-essential or non-required. Source activity,
E1, sampled output, intervention results and RO outcomes are not inputs. This
prospective structural classification is not a new empirical essentiality test
and does not replace existing state/essentiality certification prerequisites.

I §5.2's static analysis relations are proof evidence, not additional raw V3.2
semantic occurrences or ontology EDGEs. An analysis-relation ID is never an owned
support occurrence ID. Only an actual raw NODE/EDGE occurrence can satisfy §4.

### 3.3 Necessity, not incidence or unrestricted reachability

For each directly selected contract occurrence, reconstruct its connected
realization obligations from the unchanged graph and frozen grammar. Mandatory
relations are its exact expression operands/ports and bindings, declared domain
decoder components, required guard/control context, bounded-loop bound/index/step
relations, and required read/write/reaching/loop-carry/cross-pass/output relations
where specified by that contract. Expand these obligations to their stipulated
prerequisites, preserving original order, repeated elements and complete static
state joins/fixed points. No feasible or case-conditioned pruning is allowed.

A support element is necessary ONLY if it is TASK_ESSENTIAL and its exact
element occupies a mandatory relation/component of at least one such realization.
The verifier must reconstruct that relation and its prerequisites; a path is a
witness to an already mandated relation, not a rule that all reachable elements
are required. Adding all incident edges, taking arbitrary transitive closure, or
marking an edge necessary because selected endpoints exist is prohibited.

The accepted grammar/state rules determine the mandatory relation; this proposal
does not license a new algebra, effect analysis, dependency category or arbitrary
necessity oracle. If the contract/grammar does not determine that obligation
uniquely, support eligibility is UNRESOLVED. If a mandatory relation is missing
from the prospectively task-essential set, contract completion is unresolved or
invalid; it cannot be repaired by tagging candidate elements after observation.

## 4. Exact direct-support admission and bidirectional bridge

Direct-support accounting is valid ONLY when ALL of the following hold:

1. The source element is an individually addressable semantic NODE or EDGE in
   the complete original raw inventory, with valid parse/type/domain/binding.
2. It has no selector-satisfying ownership entry. Selector ownership takes
   precedence as specified in §7; simultaneous submitted ownership rejects.
3. Its graph reference resolves to exactly one TASK_ESSENTIAL element of the
   unchanged, prospectively bound contract, with §3's positive derivation.
4. Semantic kind, operation/relation, datatype, operand/result types, direction,
   endpoint roles, exact port, binding, enclosing region and loop/pass/temporal
   state context correspond exactly. Source EDGE endpoints must be the mapped
   counterparts of the actual contract EDGE endpoints, not merely same-role
   nearby nodes. Original occurrences and repeated ports are not collapsed.
5. It belongs to the same verified complete connected direct realization as at
   least one source occurrence with a valid direct selector-satisfying entry.
6. Its exact contract element is mechanically necessary under §3.3; adjacency,
   incidence, reachability or presence in both graphs alone is insufficient.
7. It is ordinary direct correspondence, not source-only extra structure.
8. Neither output equality nor sampled execution is a proof premise.
9. It is not owned by an invoked authorized equivalence's internal membership.
   Any licensed binding/alpha or surrounding equivalence proof retains ALL its
   original preconditions; this array cannot replace those proofs.
10. Original source/contract graph, state, overlap, scaffold and E5 views retain
    it. Accounting does not prune or rewrite those views or waive other gates.
11. It creates no requirement, key, attachment, multiplicity or exposure credit.
12. All typed references and evidence reconstruct independently and close under
    D/I's unchanged file identities, stages and provenance rules.

Contract → source: EVERY task-essential contract graph element must have its
required direct realization or a realization accounted for under an actually
invoked existing authorized equivalence, preserving boundaries and multiplicity.
Ordinary direct graph correspondence is injective over distinct graph elements;
distinct contract elements cannot silently collapse onto one source occurrence.
Several selectors may legitimately refer to the same contract element without
duplicating that element. A many-to-one or transformed realization needs the
existing equivalence rule, not direct-support permission.

Source → contract/accounting: EVERY raw semantic source occurrence needs exactly
one lawful final bucket. A support entry must resolve to its exact task-essential
contract element. A source-only live edge with mapped endpoints cannot be absorbed.
It must independently satisfy an actual prospective selector, belong to verified
equivalence-internal structure, pass S's independent RO rules, or remain uncovered
and fail. Finding no selector is not a finding of non-requirement.

## 7. Four-bucket reconstruction and one owner

Independently reconstruct valid memberships, not merely submitted labels:

```text
DIRECT = valid direct selector owners UNION valid direct-support owners
EQUIVALENT = valid existing authorized-equivalence selector owners
INTERNAL = valid members owned by those same invoked equivalences
```

For a source occurrence already satisfying a direct selector, its existing
direct entry owns it. Structural support references may use that occurrence as

precludes direct-support ownership; transformed internals follow equivalence.

This precedence defines deterministic production, NOT a way to discard duplicate

references are not disposition claims and do not duplicate ownership.

PASS requires exactly one VALID owner in those four buckets for EVERY semantic
source occurrence, complete contract → source realization, exact selector-only
multiplicity/attachments, all invoked equivalences and RO certificates valid,
and empty uncovered/duplicate inventories. Contract → source completeness is
checked independently of source bucket counts; owning every source element cannot
hide a missing required contract element.

Known invalid support uses existing `V32_REQUIRED_MAPPING_INVALID` and, as
applicable, malformed/reference/context/uncovered/duplicate codes. Missing
